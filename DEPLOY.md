# Деплой на Vercel

Инструкция по развёртыванию приложения на Vercel с базой данных Postgres (Neon).

## Архитектура синхронизации

Приложение синхронизирует данные между устройствами через сервер, а не напрямую (P2P/WebRTC не используется — такой подход требует одновременного онлайна обоих устройств, что не подходит для асинхронного сценария использования).

Как это устроено:

- `migrations/0001_app_state.sql` — таблица на одну строку с данными приложения (задачи, вишлисты, капсулы времени и т.д. хранятся единым JSON)
- `src/lib/sync/state.server.ts` — эндпоинт `/api/state`: читает и пишет эту строку
- `src/routes/api/state.ts` — монтирует эндпоинт
- `src/lib/sync/client.ts` — опрашивает `/api/state` каждые 8 секунд, а также сразу при возврате в приложение (фокус вкладки, пробуждение экрана); отправляет локальные изменения с небольшой задержкой (400 мс)
- `src/components/shell.tsx` — подключает синхронизацию в корне приложения

## Шаги деплоя

Порядок шагов 1–2 важен.

### 1. Запушить код в GitHub

Обновить существующий репозиторий или создать новый — публичный или приватный, не принципиально.

### 2. Подключить Neon Postgres — до первого деплоя

Это единственный шаг, где порядок критичен. Если на момент сборки в проекте не будет переменной `DATABASE_URL`, приложение молча откатится на временную встроенную базу (PGLite), которая не рассчитана на serverless-окружение и не обеспечивает постоянное хранение данных. Проблема не будет заметна снаружи — приложение продолжит работать, но данные не сохранятся между сессиями.

Как подключить:

1. Vercel Dashboard → **Add New** → **Project** → выбрать репозиторий
2. **До нажатия Deploy** открыть **Storage** → **Marketplace** → **Neon** → **Continue**
3. Создать новую базу данных

Neon автоматически пропишет переменную `DATABASE_URL` в Production и Development — вручную копировать не нужно.

> Если деплой уже был выполнен без базы: подключите Neon тем же способом через **Storage → Marketplace**, затем выполните **Redeploy** из вкладки **Deployments**.

### 3. Deploy

Таблица создаётся автоматически: команда сборки в `package.json` включает `db:migrate`, которая применяет `migrations/0001_app_state.sql` при каждой сборке.

### 4. Открыть приложение на обоих устройствах

Устройство, которое откроет приложение первым, «засеет» базу своими локальными данными. Второе устройство подтянет их при следующем опросе — в течение 8 секунд, либо мгновенно, если открыть приложение уже после того, как первое устройство успело записать данные.

## Поведение синхронизации

- Партнёры не обязаны быть онлайн одновременно — данные хранятся в базе постоянно, а не только во время активного соединения.
- Изменение, внесённое в 14:00, будет ждать в базе сколько угодно и появится у второго пользователя, как только тот откроет приложение — даже на следующий день.
- При конфликте (оба отредактировали данные без сети одновременно) побеждает версия, сохранённая на сервер последней — целиком, а не по отдельным полям. Версия, которая пришла раньше и не совпала с текущим состоянием на сервере, отклоняется с ошибкой 409 и подтягивает актуальную версию вместо того, чтобы её молча перезаписать.
- Тайное голосование и капсулы времени хранятся в той же общей записи в базе. Интерфейс скрывает чужой голос до момента, пока не проголосуют оба, но сами данные уже находятся на сервере — это вопрос доверия между пользователями, а не технической гарантии приватности.

## Опционально: авторизация

В проекте уже реализована `better-auth`, но по умолчанию выключена (`.grok/app-env.json` → `VITE_AUTH_ENABLED: false`). Включение авторизации — отдельная задача, не входит в базовую настройку деплоя.

## Флаг `deploy.database` в `.grok/app-env.json`

Значение `false` — это метаданные для платформы Grok (указывают её собственному хостингу, нужно ли провижинить базу при деплое через эту платформу). На деплой через Vercel этот флаг не влияет: код ориентируется только на переменную окружения `DATABASE_URL`.
